# Errand Agent — Concepts Brief

- **Author:** Aldrin Joseph
- **Date:** 2026-11-22
- **Revision:** 2 — rewritten after four Goldfish lens reports (contrarian, cost,
  inventive catalyst, readiness). What changed is listed at the end.
- **Mode:** BRAINSTORM, consolidated (no interactive gates)

## Overview

A local chat agent that books home services — plumber, electrician, AC servicing —
against a fixed, deliberately unreliable mock tool environment. The graded ask is
not conversation quality. It is whether the agent stays correct when the user is
vague, the price moves after approval, `book` times out after possibly succeeding,
a provider review contains instructions, the process restarts mid-booking, and a
50-row memory store has to be squeezed into a fixed model context.

## Goals vs. Non-Goals

**Goals**
- Turn a vague request into a verified booking, or an explained non-outcome, from
  a closed set of 13 outcome tokens.
- One conversational path covering book, **cancel and reschedule** — all three are
  consequential actions requiring the same digest-bound approval.
- Approval enforced by application code; any material change voids it.
- One booking per approved action across repeated confirmations, retries and
  process restarts; ambiguous timeouts resolved only from `get_booking_status`.
- Untrusted review text can change what is displayed, never what is permitted.
- **Proactive follow-up when a provider cancels with no user turn present** —
  detect, notify, find a replacement within known preferences, and obtain fresh
  approval before rebooking.
- Memory inspectable, correctable, forgettable, with forgotten and unconfirmed
  facts provably absent from every context manifest.
- **Nine** trace invariants, **32** offline scenarios, an eval table generated by
  the test run.
- Evidence that a real model actually drove the tool calls, not a `switch`.

**Non-Goals**
- Real integrations, payments, identity, multi-tenant concurrency.
- A web UI, vector memory search, learned inference, an unattended auto-booking
  path (the proactive path deliberately stops at approval).
- Agent framework adoption.

## Analysis

**The load-bearing decision.** The brief demands a real LLM driving tool calls and
demands that approval not be inferred from model output. Those coexist only if the
model's action space is restricted per state by code and the side-effecting tools
are gated by an approval row. A free-form ReAct loop with a post-hoc approval check
fails the exact scenario the brief sets up, because a prompt-level rule is not an
enforcement mechanism.

**The corrected framing of "two independent blocks."** A reviewer was right that
the earlier draft described one check three ways: not offering the tool, refusing
it at the gateway and refusing it at the approval store all read the same persisted
`state` and `digest`. Two blocks are now genuinely independent: a **call-site
monopoly** (`execute_if_approved` is the only importer of the side-effecting tool,
proven by a grep test) and a **runtime refusal** at the gateway keyed on an
unconsumed approval token for the live digest. Neither subsumes the other.

**The evidence inversion.** Thirty-two scripted scenarios would pass identically
against a `switch` statement. That is the honest weakness of a scripted suite, and
the answer is not more scenarios: it is `I8` (every `tool_call` must match the
`action_returned` of the preceding `llm_call`) plus `run_config.llm_mode` on every
run, so a grader can see which runs a model drove and which were scripted for
determinism.

**Approval must not depend on the model it constrains.** Reply classification is a
pure function over a closed phrase list, not a model call. A model classifier would
add a paid call and put the approval path back inside the untrusted model. Negative
patterns win, so "yes but not before 10" is not an approval.

**Money, ids and digests are correctness surfaces, not plumbing.** Float money makes
approval invalidation nondeterministic. A digest over `json.dumps(asdict(action))`
raises `TypeError` on the first `datetime`, so canonicalisation is explicit.
`uuid5(None, digest)` raises `AttributeError`; the namespace is a fixed constant.
And an idempotency key derived only from the action digest would swallow a
legitimate rebooking after a cancellation as a duplicate, so `attempt` is part of
the payload.

**Contradictions surfaced and accepted.**
- One-page design note vs. a multi-page working spec: the condensed note is a
  separate artifact written to its limit; the spec is internal material.
- "Three real bugs" cannot be written in advance. The bug log opens empty at Phase
  1 and each entry starts as a failing test.
- "Forgotten facts must never reach the model" vs. "log what context was sent":
  the manifest records ids and exclusion reasons, never values. Otherwise the trace
  becomes the leak.
- "A real LLM drives tool calls" vs. deterministic offline evals: both modes are
  recorded per run rather than pretending the scripted suite exercises the model.

**Where complexity was cut.** `MANAGE_APPROVAL`/`MANAGE_EXEC` collapsed into the
existing approval pair with a `kind` on the action. `RECOVERY` stopped being a state
and became a `mode` flag on the same search→hold→approve path. Cancel and
reschedule needed no new machinery once approval was kind-agnostic.

## Alternatives Weighed

- Free-form ReAct with post-hoc approval — rejected by author: the invariant would
  be a prompt instruction, breakable by the injection scenario.
- LangGraph/CrewAI graph — rejected by author: hidden framework state weakens the
  restart and context-audit guarantees and adds version drift to an offline suite.
- Model-judged approval or model reply-classifier — rejected by author: the
  approval path would depend on the model it exists to constrain.
- User-typed confirmation digest — rejected by author: stronger binding, unusable UX.
- Float money — rejected by author: rounding drift creates spurious invalidations.
- Embedding memory retrieval — rejected by author: nondeterministic offline, cannot
  be pinned in a fixture.
- Web UI — rejected by author: no graded property behind it.
- Second LLM agent on the proactive path — rejected by author: it must fire with no
  user turn, and rules suffice.
- Blind retry of `book` on timeout — rejected by author: the double-booking bug.
- HMAC capability token instead of a digest row — considered and not adopted: it
  buys tamper-evidence a local mock cannot test, at the cost of a key to manage.

## Key Decisions & Staging for Next Steps

1. Constrained action selection with a per-state legal-tool set; approval as a
   frozen action + sha256 digest + `attempt` discriminator.
2. FSM in SQLite, 9 states, intent row written before the side effect; startup
   reconciliation through `get_booking_status`.
3. Reply classification is a pure function; the side-effecting tools are reachable
   only through `execute_if_approved`, enforced by both a grep test and a runtime
   token check.
4. Memory admission filter at query time; per-turn manifest with ids and reasons
   only; measured context slices with a 300-token reserve.
5. Injection containment is structural; pattern scanning is logging only.
6. Proactive path: poll-with-`tick()`, outbox, always fresh approval, never
   unattended booking.
7. Build order: mocks → store/policy/approval → context/memory/trace → orchestrator
   → 32-scenario harness → CLI → watcher → deliverables.
